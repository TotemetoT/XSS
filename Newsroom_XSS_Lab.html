How does it work?
The sample uses an image with invalid image data. Loading fails, so its onerror handler runs JavaScript that changes the headline or notice. The vulnerable renderer treats the stored comment as HTML instead of text.
You can change the message inside the sample. For the automatic check, keep its target as headline or notice. Other custom experiments are allowed but may not trigger the checklist.


3 / Visit as another reader
Click Open as another visitor above the news page or below. The attack should run again from the stored comment—even though this is a fresh document.
Waiting for the attack to affect another visitor.


4 / Fix the vulnerable code
Edit the code box directly below. You do not need Inspect Element, a separate editor, or the downloaded file's source.
  1. Find return comment; in this code box.
  2. Replace that line with return escapeHTML(comment);.
  3. Keep the surrounding function lines.
  4. Click Deploy renderer.
Raw comments are currently inserted into HTML.
Why does this repair work?
escapeHTML converts markup characters into character references. The browser displays the comment as plain text instead of interpreting it as tags and event handlers. This helper is already provided; you only need to call it.
This small editor supports the vulnerable function and this repaired function. It switches the real rendering logic used for future simulated responses. It is not a general-purpose code editor. Escaping here is for text inside HTML elements; other contexts need appropriate protections.


5 / Restore the original headline
After deploying the fix, click the button below. It loads a fresh page with the original headline and notice, using the repaired renderer. The malicious comments stay in the database and should appear as text.
Deploy the repair first. Fixing the renderer does not undo a page already changed by an attack.


6 / Try the attack again
  1. Click either attack button from Step 2, or the shortcut below.
  2. Click Post comment on the news page again.
  3. Verify that the original headline and notice remain, and the new payload appears as plain text.
Waiting for a new sample attack to be posted after restoration.

Instructor notes
Suggested pacing: normal comment 2 minutes; injection 3; new visitor 2; repair 3; restoration and retest 3; explanation 2.
Stored XSS saves malicious content, not necessarily a modified server HTML file. The browser executes it when it parses a vulnerable response. Output escaping fixes this text context without deleting the saved record.
Checklist observations are classroom feedback, not a security audit. Reference: OWASP XSS Prevention Cheat Sheet.
